nabc-dev

Du besoin à la fusion, sans rien laisser au hasard.

Le plugin Claude Code de Not a Bad Company. La qualité est garantie par des scripts, pas par des consignes : ce que Claude oublie, un hook le rattrape. La relecture et la fusion restent humaines.

Trois couches

Les invariants valent partout, le plugin est identique d'un projet à l'autre, et chaque projet ne décrit que ce qui lui est propre.

La guideline générale

Les règles qui ne dépendent d'aucun projet : français, commits conventionnels, tests d'abord, rien n'est « fait » sans preuve.

Une fonctionnalité : /nabc-dev:feature

Chaque étape est confiée à un agent en contexte séparé. Les pastilles jaunes sont les moments où la chaîne s'arrête et attend Antoine.

  1. 1

    Spec BDD

    spec-analyst

    Scénarios Given / When / Then écrits depuis le besoin, le code réel et les ADR. Les questions remontent avant la rédaction.

    Arrêt. Antoine valide la spec explicitement.
  2. 2

    Tests d'acceptance

    test-writer

    Un test par scénario, rouge pour la bonne raison. Ensuite ils sont figés : le hook interdit à tout autre agent de les modifier.

  3. 3

    Plan

    implementation-planner

    Changements minimaux, fichier par fichier. Une « question de spec » dans le plan renvoie à Antoine, et à l'étape 1 si la réponse change la spec.

  4. 4

    Implémentation

    code-implementer

    Tests unitaires d'abord, jusqu'à ce que les tests d'acceptance passent. À chaque fichier écrit, l'analyse statique tourne.

  5. 5

    Vérification

    /nabc-dev:verify

    Des tests verts ne prouvent pas que le produit marche : la vérification finit toujours dans un vrai navigateur.

    gatemutationCRAP des méthodes modifiéesparcours E2E de référencenavigateur réel
  6. 6

    Revue contre la spec

    code-reviewer

    Contexte neuf : l'agent reçoit la spec et le diff, rien d'autre. Il juge le résultat, pas les intentions. Verdict CONFORME ou À CORRIGER.

    À CORRIGER → code-refactorer, puis retour à l'étape 5. Au troisième aller-retour, arrêt et intervention manuelle.
  7. 7

    Livraison

    /nabc-dev:finish

    Audit des secrets sur tout l'historique, spec marquée livrée, commits vérifiés, description de PR, worktrees nettoyés.

    Arrêt. La fusion est faite par Antoine.

Les autres entrées

Lancées à la demande, jamais automatiquement.

/nabc-dev:initUne fois par projet

Écrit nabc.json depuis un preset, la gate, le CLAUDE.md court et la CI. Pose les règles d'architecture du domaine et de l'application, avec l'ADR du découpage des couches à trancher et la dette existante en baseline. Ne remplace rien sans montrer le diff.

/nabc-dev:crap [--changed]Pour savoir où un changement est dangereux

CC² × (1 − couverture)³ + CC par méthode, pire en tête, avec l'action : couvrir jusqu'à N %, ou découper.

/nabc-dev:maintenanceAprès une phase de rush

Réparer → mesurer → couvrir → mutation → auditer → refactorer, avec un critère d'acceptation à chaque marche.

/nabc-dev:parallelUn chantier en lots indépendants

Un worktree par agent, fusion validée lot par lot.

/nabc-dev:secrets-auditAvant un push

Secrets et données personnelles sur tout le dépôt et tout l'historique, avec la conduite à tenir si la fuite est déjà publiée.

/nabc-dev:context-auditUne fois par mois

Retire du CLAUDE.md, des agents et des skills les chiffres périmés, les cartes du code et les chemins morts.
